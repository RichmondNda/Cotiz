## Objectif

Se connecter aux trois espaces avec une session sûre, activer un compte avec un code remis par une personne, réinitialiser un mot de passe sans fournisseur.

## Périmètre

### Tables créées

Définition cible dans [`specs/schema.sql`](../specs/schema.sql) (rechercher `lot 1.1`), dictionnaire dans [`specs/data-model.md`](../specs/data-model.md).

- `users` — Toute personne qui se connecte : super-admin, gestionnaire ou souscripteur. Une seule identité par personne, quel que soit le nombre d'associations.
- `credentials` — Secrets d'authentification, séparés de l'identité pour limiter leur exposition.
- `sessions` — Sessions de connexion (jetons de rafraîchissement).
- `one_time_codes` — Codes d'activation, de réinitialisation et d'invitation. Sans fournisseur : le code est remis par une personne (gestionnaire, super-admin).
- `password_reset_requests` — Demandes « mot de passe oublié ». Sans fournisseur, elles sont traitées par le rôle supérieur qui émet un code.
- `platform_staff` — Personnel de la plateforme Cotiz.

## Étapes

Une étape = une PR. Commande : `/etape 1.1 <n>`.

### Étape 1 · Tables identity

Migrations `users`, `credentials`, `sessions`, `one_time_codes`, `password_reset_requests`, `platform_staff` d'après `schema.sql` (politiques RLS de `one_time_codes` et `password_reset_requests` incluses ; les clés étrangères vers `associations` sont ajoutées au lot 1.2). CLI `create-platform-owner`.

**Vérification :** Tests d'isolation sur les deux tables à RLS ; la CLI crée un owner plateforme avec code d'activation

### Étape 2 · Connexion

`auth.login` (`POST /auth/login`) : argon2id, espace vérifié (`platform` via `platform_staff` dès ce lot ; `association` et `subscriber` via `memberships` à partir du lot 1.2), verrouillage 5 échecs / 15 min, messages identiques (`invalid_credentials` / `wrong_space`), limitation par IP. JWT EdDSA 15 min + jeton de renouvellement en cookie.

**Vérification :** Tests : bon mot de passe, mauvais, compte inconnu (même temps de réponse ± 50 ms), verrouillage

### Étape 3 · Renouvellement et déconnexion

`auth.refresh` avec rotation ; réutilisation → révocation de la famille ; `auth.logout` + liste noire Redis du `sid`.

**Vérification :** Test : rejouer un ancien jeton révoque toute la famille

### Étape 4 · Gardes

`JwtGuard`, `SpaceGuard` (un jeton `platform` ne passe jamais sur `/associations/*`), `MembershipGuard` (branché sur `memberships` au lot 1.2), `PermissionGuard` + `@Can()` alimenté par `permissions.yaml`.

**Vérification :** Tests de chaque garde

### Étape 5 · `GET /me`

`me` : identité, espace, associations et rôles, `permissions`, `features` (depuis `features.yaml` et le plan).

**Vérification :** Réponse conforme au contrat

### Étape 6 · Service de codes

`CodeService` : génération (alphabet sans ambiguïté, 8 caractères ou 6 chiffres), hachage, chiffrement réversible pour l'activation (`shared/crypto`, AES-256-GCM, clé en variable d'environnement), 5 essais, invalidation des codes précédents, `handoff` (message, liens `wa.me`, `sms:` et `mailto:`).

**Vérification :** Tests unitaires ; le code n'apparaît jamais dans les journaux

### Étape 7 · Activation

`auth.activate` : identifiant (email ou téléphone) + code + mot de passe (10 caractères minimum, liste de mots de passe courants embarquée → `weak_password`) ; code consommé, compte actif, session ouverte, `user.activated`. Sert au super-admin (CLI), aux gestionnaires (approbation, lot 1.3) et aux souscripteurs (lot 2.3).

**Vérification :** Code expiré, réutilisé, 6e essai : refusés ; l'owner créé par la CLI s'active et se connecte

### Étape 8 · Mot de passe oublié sans fournisseur

`auth.forgot` (réponse identique dans tous les cas, 3 demandes / 24 h, crée `password_reset_requests`), `auth.verify`, `auth.reset` (révoque toutes les sessions). CLI `reset-password <email>` pour le super-admin. Les écrans de traitement arrivent aux lots 1.4 (gestionnaires) et 3.1 (souscripteurs).

**Vérification :** Parcours testé avec un code émis par un service de test : demande → code → nouveau mot de passe → anciennes sessions invalides

### Étape 9 · Tâche d'expiration

`codes.expire` : codes et demandes expirés, `code_encrypted` effacé.

**Vérification :** Test avec horloge simulée
