## Périmètre

### Tables créées

Définition cible dans [`specs/schema.sql`](../specs/schema.sql) (rechercher `lot 1.2`), dictionnaire dans [`specs/data-model.md`](../specs/data-model.md).

- `associations` — Le client de Cotiz. Racine de l'isolation multi-tenant.
- `association_payment_methods` — Comment les souscripteurs paient l'association (écran onboarding étape 3).
- `memberships` — Lien entre une personne et une association, avec son rôle. Un souscripteur dans deux associations = deux lignes.
- `plans` — Formules d'abonnement gérées par le super-admin.
- `subscriptions` — Abonnement en cours d'une association.

## Étapes

Une étape = une PR. Commande : `/etape 1.2 <n>`.

### Étape 1 · Tables tenancy

`associations`, `association_payment_methods`, `memberships` avec leurs politiques RLS ; clés étrangères différées des lots 0.5 et 1.1 vers `associations`.

**Vérification :** Tests d'isolation sur les trois tables ; `rls-smoke-test.sql` passe sur la base migrée

### Étape 2 · Tables billing

`plans`, `subscriptions` (index unique d'abonnement actif).

**Vérification :** Migrations

### Étape 3 · Appartenances et connexion

`MembershipGuard` branché sur `memberships` ; connexion `association` et `subscriber` activée dans `auth.login`.

**Vérification :** Tests de connexion pour les trois espaces

### Étape 4 · Plans

`pf.plans`, `pf.plan.write`, `pf.plan.archive` : quotas, `features` (liste de `features.yaml` marquées planGated), archivage sans casser les abonnements ; `pub.plans` (cache 1 h).

**Vérification :** Un plan archivé n'est plus dans `pub.plans` mais reste appliqué

### Étape 5 · Service de quotas

`QuotaService.assert(associationId, 'projects' | 'subscribers' | 'managers')` avec cache 5 min, invalidé par `subscription.plan_changed`.

**Vérification :** Tests
