## Étapes

Une étape = une PR. Commande : `/etape 1.3 <n>`.

### Étape 1 · Table

`association_requests`.

**Vérification :** Migration

### Étape 2 · Formulaire public

`pub.request` (`POST /public/association-requests`) : validation, référence `DEM-2026-00042`, anti-abus sans tiers (champ piège, ALTCHA auto-hébergé via `altcha-lib`, limitation par IP), `Idempotency-Key`.

**Vérification :** Un envoi sans défi ALTCHA valide → `challenge_failed`

### Étape 3 · Pages légales

`pub.legal` (Markdown versionné dans `backend/content/legal/`).

**Vérification :** Réponse conforme

### Étape 4 · File de traitement

`pf.req.list` (filtres + `facets`), `pf.req.get`.

**Vérification :** Tests de permission : `support` lit, ne décide pas

### Étape 5 · Approbation

`pf.req.approve` : transaction de architecture/04 §4.1 (rôle `cotiz_platform`) : association, abonnement, gestionnaire, appartenance owner, code d'activation ; réponse avec `handoff` (identifiant, code, message prêt, liens `mailto:` et WhatsApp) ; idempotente.

**Vérification :** Approuver deux fois → un seul espace ; le gestionnaire active son compte avec le code et se connecte

### Étape 6 · Refus et création directe

`pf.req.reject` (code et message) ; `pf.asso.create` (même cas d'usage de fond que l'approbation, sans demande).

**Vérification :** Impossible de refuser une demande approuvée ; création directe testée
